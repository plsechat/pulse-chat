# Federation — wire protocol and invariants

How two Pulse instances peer, share servers, and relay users, DMs, and
E2EE material. Server code: `apps/server/src/http/federation*.ts`
(inbound endpoints), `apps/server/src/utils/federation*.ts` (keys,
tokens, outbound fetch, outbox, dispatchers),
`apps/server/src/routers/federation/` (operator/user tRPC surface),
`apps/server/src/crons/federation-*.ts` (outbox drain, replay-state
prune).

## Identity and trust

- **The advertised domain is canonical.** An instance is identified by
  `config.federation.domain` — the value it advertises, not whatever
  host a request happens to arrive on. Peer rows, token issuers, and
  discovery all key on it. A peer's `domain` is validated as a bare
  `host[:port]` (≤ 253 chars) before it is stored; it is later
  interpolated into every outbound URL for that peer.
- **One EdDSA (Ed25519) keypair per instance**, generated by the
  instance owner (`federation.generateKeys`), stored in
  `federation_keys`. Public keys are exchanged at peering time and
  pinned in `federation_instances`; later requests are verified
  against the pinned key. A peer's key is stored only if it is a
  ≤ 2 KB JSON Web Key with `kty: "OKP"`.
- **Two kinds of signed material**, both EdDSA under the instance key:
  - *User federation tokens* (`generateFederationToken`) — JWTs with
    `iss` = advertised domain, `aud` = target domain, `sub` / `name` /
    `avatar` / `publicId` claims and a 24 h expiry. They carry **no
    `jti`** and there is no replay window for them: within its lifetime
    a captured token can be presented again. Treat it as a bearer
    credential scoped to one audience. An expired token closes the
    socket with `FEDERATION_TOKEN_EXPIRED` (4005), which the client
    answers by re-minting through its home instance; any other failure
    is `FEDERATION_REJECTED` and permanent.
  - *Request signatures* (`signChallenge` / `verifyChallenge`) on the
    server-to-server endpoints — canonicalized JSON (sorted keys) with
    the body's `sha256`, `iss`, `aud`, a 5-minute expiry (60 s clock
    tolerance) and a random `jti`. Seen `jti`s are persisted in
    `federation_seen_jti` (`INSERT … ON CONFLICT DO NOTHING` is the
    atomic check) until `exp` + tolerance and pruned by the
    `federation-seen-jti` cron, so a replay survives a restart. Replay
    protection exists **only** here.
- **publicId is the only cross-instance user identity.** Numeric row
  ids never travel as identity — both sides mint their own serials, and
  `/federation/user-info` answers by publicId only. A remote user
  materializes locally as a **shadow user** looked up (or created) by
  `(home instance, publicId)` and nothing else
  (`findOrCreateShadowUserByPublicId`); the peer's numeric id is stored
  as informational text and never used as a lookup key.
- **A user's home instance is the only party that can vouch for them.**
  `/federation/user-info` answers only for users homed on the responding
  instance, and the response is signed. A peer announcing a group DM
  with members homed on a *third* instance does not get them minted on
  its say-so: the receiver asks that third instance (which must be an
  active peer of its own) and takes *its* name, or skips the member
  (`verifyRemoteUserAttestation`).

## Peering lifecycle

`pending → active` (or `blocked`), direction `outgoing | incoming |
mutual`. All instance-level peering operations (add / accept / block /
remove / list, config, key generation and rotation, outbox retry) are
gated on `instanceOwnerProcedure` — the bootstrap-server owner alone,
never per-server permissions.

1. A's owner adds B by domain → `GET /federation/info` (B's identity,
   public key and version) → `POST /federation/request` (A introduces
   itself; B reverse-fetches A's `/federation/info` and refuses a key A
   does not serve there). B caps its approval list at 50 pending
   incoming requests (429 beyond).
2. B's owner accepts → `POST /federation/accept` (signed, through B's
   outbox) → both sides hold pinned keys, status `active`. Each side
   records the other's advertised `version` at this point.
3. Either owner can end it: remove / block / `federation.setConfig`
   (disable) sends a best-effort `POST /federation/unpeer
   { reason: 'removed' | 'blocked' }` before tearing down locally. The
   receiver sets its row to `blocked`, sweeps the shadows it minted for
   that peer together with the DM channels that only existed because
   of them (1:1s left with one member, group mirrors left empty — mixed
   groups keep their local members and history), and publishes
   `FEDERATION_INSTANCE_UPDATE`. Idempotent.

### Key rotation

`federation.rotateKeys` (owner) inserts a new key, marks the old one
`retired_at`, and queues `POST /federation/key-rotation
{ newPublicKey, rotatedAt }` to every active peer **signed with the
retired key** — the only key the peer has pinned. The receiver verifies
the signature with its pinned key, independently fetches the peer's
`/federation/info` and refuses unless it advertises the announced key,
then moves `public_key → previous_public_key`, stamps `key_rotated_at`
and pins the new key. For **24 h** after that (`FEDERATION_KEY_GRACE_MS`)
both keys verify incoming signatures, so relays the peer signed before
switching (or still queued in its outbox) are not refused; the retired
private key stays on the rotating side for the same window so queued
rotation announcements can still be signed, after which the
`federation-seen-jti` cron removes it and any undelivered announcement
is dead-lettered (re-peer by hand). A re-`POST /federation/request`
with a new key from an existing peer re-pins the same way, after the
reverse fetch.

## Endpoint inventory (`apps/server/src/http/index.ts`)

Every `POST /federation/*` route except `/request` runs the shared
prologue (`authorizeFederationRequest`): federation enabled → 1 MB body
cap → sender row by `fromDomain` (status `active` unless the route says
otherwise) → signature over the whole body minus `signature`, checked
against the pinned key and the previous key inside its grace window →
per-peer budget. `/request` is the one unauthenticated route (the key
arrives in the body and is proven by the reverse fetch).

| Group | Endpoints | Notes |
| --- | --- | --- |
| Peering | `GET /federation/info`, `POST /federation/request`, `/accept`, `/unpeer`, `/key-rotation` | `/accept` admits a `pending` sender row (we requested); `/unpeer` admits a `blocked` one (idempotent repeat) |
| Discovery | `POST /federation/servers`, `/shares-server`, `/directory` | All signed requests with signed responses; `/servers` lists federatable servers with one grouped member count; `/directory` answers the public-directory listing (≤ 200 rows, `limit` optional) — a signed empty list when the owner has not exposed the directory. Peers pull it daily and refresh counts hourly into `directory_cache` (`crons/directory.ts`); rows go with the peer |
| Users | `POST /federation/user-info`, `/user-info-update`, `/report-user` | `user-info` is publicId-only, local users only, signed response |
| Social | `POST /federation/friend-request`, `/friend-accept`, `/friend-remove` | Unknown subjects and blocks are `200 { ignored }` |
| DMs | `POST /federation/dm-relay`, `/dm-group-create`, `/dm-group-add-member`, `/dm-group-remove-member`, `/dm-channel-state-update` | see *DM relay* |
| E2EE | `POST /federation/get-prekey-bundle`, `/dm-sender-key`, `/channel-sender-key-notify`, `/identity-rotation-broadcast` | see `e2ee-sender-keys.md` |
| Moderation | `POST /federation/member-removed` | see *Moderation propagation* |
| Announcements | `POST /federation/announcement-follow`, `/announcement` | see *Announcement follow* |

Remote users also join servers live over WS: a federated client opens a
WS to the remote instance authenticated by federation token (no
handshake/join), and the remote side resolves it to the shadow user.

### Response conventions

- `200 { ignored: '<reason>' }` means "verified, understood, and
  deliberately not applied": unknown recipient/subject, a block, a
  stranger's first DM, a non-member posting into a group mirror, a
  repeated acceptance. The sender's outbox treats it as delivered and
  existence is never disclosed by status code.
- `4xx` is a protocol error the sender can fix (`400` malformed, `401`
  bad signature, `403` not a trusted peer / refused, `409` ordering gap
  — see dm-relay, `429` over budget with `Retry-After`).
- `404` is reserved for "this instance does not have that route": the
  sender's outbox dead-letters on it at once.

### Bounds at the trust boundary

A peer is authenticated, not trusted. Every peer-supplied value is
bounded before it is stored or forwarded (`http/federation-helpers.ts`;
the same caps apply again inside `findOrCreateShadowUser*` and the
profile pull): display names 32, bios 500, server/group names 100,
`bannerColor` must be a hex colour, publicIds 64, DM content
`MAX_MESSAGE_WIRE_LENGTH` (the local cap), SKDM distribution messages
16 KB, identity keys 128, group announcements ≤ 100 members, SKDM
recipient lists ≤ 500, report text 1000, avatar file names a bare
`[A-Za-z0-9._-]` name. Display strings are truncated; structural fields
(ids, keys, arrays, enums) are rejected with `400`.

### Per-peer rate limits

Two layers. The per-IP fixed-window limiter in `http/index.ts` is the
pre-auth flood brake (60/min per address and route; `/federation/info`
and `/federation/servers` have their own read bucket). After the
signature verifies, a **per-peer** bucket keyed on `fromDomain` applies:
300/min across all signed routes, and a separate 120/min for
`/federation/dm-relay`. Over budget → `429` with `Retry-After`; the
peer's outbox defers the row by that value without counting an attempt.
Unsigned traffic cannot drain a peer's budget.

## Outbound discipline

- All outbound calls go through `federationFetch`
  (`utils/federation-fetch.ts`). It resolves the host, applies the
  private-range/allowlist check to every A/AAAA answer, and **dials the
  validated address** with `Host` and TLS SNI/`checkServerIdentity` set
  to the hostname, so a DNS answer cannot change between validation and
  connect. IP-literal peers (allowlisted via
  `FEDERATION_ALLOW_PRIVATE_CIDRS`, IPv4 and IPv6) skip DNS. Redirects
  are refused (`redirect: 'manual'`); bodies are read through a byte
  cap (1 MB default, `maxBytes` per call) before any JSON parse; a
  per-peer token bucket (60 burst, 1/s sustained) throttles our own
  calls to each peer.
- Signed query/response pairs (`queryInstance` → `signedJsonResponse`)
  are used wherever the response carries data a TLS-only MITM could
  substitute: pre-key bundles, user-info, server lists, co-membership.
  The response is signed for the requester's audience and verified
  against the responder's pinned key(s).
- **Every relay goes through the outbox** (`utils/federation-outbox.ts`,
  table `federation_outbox`): the row is written first, attempted once
  inline, deleted on success, otherwise retried by the
  `federation-outbox` cron (every 30 s, advisory lock 827394906) per
  peer in order with backoff 30 s → 2 min → 10 min → 1 h → 6 h. A row is
  dead-lettered after 8 attempts or 48 h, and **immediately on a 404**
  (`unsupported:<path>` — the peer runs a release without the route).
  Dead rows are shown per instance in the owner's federation panel with
  a retry action (`federation.listDeadOutbox` / `federation.retryOutbox`).
  Presence pushes are *transient* (attempted once, never persisted —
  the next status change supersedes a lost one), as is `/unpeer`.
- **Delivery is at-least-once**, so receivers are idempotent: the state
  and membership routes are naturally so; `dm-relay` carries a
  `relayId` (uuidv7) that the receiver stores in
  `dm_messages.federation_relay_id` (unique) and acknowledges without a
  second insert or event.
- Every relay outcome is mirrored onto
  `federation_instances.last_error` / `last_error_at` (`unsupported:<path>`,
  `http:<status>`, or the transport error, ≤ 200 chars) and cleared on
  the next success. `listInstances` / `listActiveInstances` expose it
  with `peerVersion` and the pending/dead outbox counts; the server rail
  shows an amber badge on a degraded peer and the federation panel the
  detail.
- Dispatch helpers (`utils/federation-*-dispatch.ts`) fan out to peers.
  Fire-and-forget relays MUST carry a `.catch` — an unguarded rejection
  inside their DB preamble is the CONNECTION_ENDED CI-flake family.

## Presence

Coming online (first live socket of a local user) pushes
`/federation/user-info-update { status }` to every peer that shares a DM
or server with that user; the last socket closing pushes `offline`
after a 5 s debounce (cancelled by a reconnect). Explicit status changes
push as before. The receiver applies the runtime status to the shadow
and publishes `USER_UPDATE`.

## DM relay

`POST /federation/dm-relay` from the sender's home to the recipient's
home. Receiver order:

1. Resolve the recipient (a *local* user by publicId; unknown → `200
   ignored`). Mint/refresh the sender's shadow.
2. A block in either direction → `200 { ignored: 'blocked' }`.
3. Group message (`federationGroupId`): route into the announced mirror.
   No mirror → `409` (the announcement is queued ahead of the message in
   the sender's outbox, so this is an ordering gap to retry, not a
   `404`). Sender not a member of the mirror → `200 ignored`.
4. 1:1: an existing channel keeps flowing. A **new** channel requires
   the same consent a local user needs to open a DM — friendship or a
   shared server (the shadow has real `server_members` rows here) —
   else `200 { ignored: 'not_permitted' }`. The channel is upserted on
   `dm_channels.pair_key` (`sorted([identity(a), identity(b)]).join('|')`
   with `local:<publicId>` / `federated:<domain>:<publicId>`), so two
   first messages crossing between the instances, or a local click
   racing the relay, land on one row.
5. An `e2ee` envelope on a plaintext channel flips it to encrypted
   (one way); the ciphertext is stored opaquely.
6. Insert with `relayId`; a duplicate acknowledges the existing message.

## Moderation propagation

Kick/ban of a federated member sends `POST /federation/member-removed`
to the member's home instance, which removes the membership locally and
notifies the user. Bans are recorded on the serving instance; the home
instance is told only about removal.

Only kick/ban propagate. **Roles are local to each instance**: a role
granted to a shadow user on the serving instance is stored and enforced
there only and is never sent to the user's home instance (nor the other
way round). Expect a remote member's roles to differ per instance.

**Reports follow the user home.** When a report filed on an instance
targets a shadow user, `reports.create` also queues `POST
/federation/report-user { subjectPublicId, reporterPublicId,
serverPublicId, kind, reason, details, messageExcerpt }` to that user's
home. The home inserts it into its own `reports` table with
`audience: 'instance'`, `source: 'federated:<domain>'`, the reporter
represented by their shadow, the excerpt as a reporter-attested
snapshot and the peer server reference appended to the details. Reports
about users not homed there are `200 ignored`.

## Announcement follow

A channel on instance B can follow an announcement channel on instance
A (`channel_follows`; see `utils/announcement-follow.ts` and
`http/federation-announcement.ts`).

- **Subscribing.** B's channel settings take the source's follow
  address `A-domain/serverPublicId/channelPublicId`. B records the
  follow (`source_instance_id` + `source_channel_public_id` +
  local target) and asks A with a signed `POST
  /federation/announcement-follow { action: 'follow', serverPublicId,
  channelPublicId, targetChannelPublicId, targetChannelName,
  targetServerName }`. A answers `200 { success, sourceChannelName,
  sourceServerName }` and records the remote follower (`target_instance_id`
  + `target_channel_public_id` + local source) when the server is
  federatable and the channel a public announcement channel; anything
  else is `200 { ignored: 'not_followable' }` and B rolls its row back.
  A peer that is down gets the request from B's outbox (B shows the
  follow as pending). `action: 'unfollow'` (B → A) and `action:
  'removed'` (A → B, when A's side drops the follower) delete the
  matching row; all three are idempotent.
- **Relaying.** Each plain user post in the source (never a poll, a
  system row or an encrypted row) is relayed to every active remote
  follower as `POST /federation/announcement { action: 'create' |
  'update', sourceServerPublicId, sourceServerName,
  sourceChannelPublicId, sourceChannelName, targetChannelPublicId,
  messageId, content, edited, author: { publicId, name, avatar } }`,
  deletions as `{ action: 'delete', sourceChannelPublicId,
  targetChannelPublicId, messageIds }` (≤ 100 ids). B applies it only
  when its own row says that target follows that source on that peer
  (`200 { ignored: 'not_following' }` otherwise). The author
  materialises as a shadow user (publicId-keyed, avatar pulled from
  A's `/public/`); the copy is a `type: 'system'` row whose content is
  a JSON document keyed by `sourceKey = A-domain:channelPublicId:messageId`,
  so a replayed create lands on the existing row and an update that
  overtakes its create still creates it. Reactions are not relayed.
  Bounds: content ≤ `MAX_MESSAGE_CONTENT_LENGTH`, names 32/100, avatar a
  bare file name, structural fields 400.

## Version compatibility

`GET /federation/info` advertises `version`. It is recorded in
`federation_instances.peer_version` at request/accept time and shown in
the federation panel; a peer that answers `404` to a route it lacks is
marked degraded (`last_error = unsupported:<path>`, amber rail badge,
dead outbox rows retryable after the peer upgrades). There is still no
negotiated protocol version or capability flags: the signed-request
format changed in v0.2.0 (`sha256` / `iss` / `aud` / `jti` claims) and
a pre-v0.2 peer cannot federate with a v0.2+ one. Any future wire change
needs the same release-note warning.

Changes in this release a peer must be on the same release to use:
`/federation/servers` is a signed `POST` (older peers' discovery lists
come back empty), `/federation/user-info` no longer accepts numeric ids
and returns a signed body, `/federation/accept` verifies the whole body
(the older `{ domain }`-only signature is still accepted), and
`/unpeer`, `/key-rotation`, `/report-user` are new (older peers answer
`404`; the rows dead-letter). v0.4.0 adds `/announcement-follow` and
`/announcement` (an older peer answers `404`; following it dead-letters
the same way, so the follow stays pending until the peer upgrades).

Remote tRPC rename with a one-release alias: the session bootstrap a
federated client calls on the remote instance is `others.openSession`
(was `others.joinServer`); the membership join is `servers.joinByInvite`
(was `servers.join`) and the "member's session connected" subscription
is `users.onConnected` (was `users.onJoin`; the event is
`USER_CONNECTED`, and becoming a member is `SERVER_MEMBER_JOIN`, now
fanned out to every member). v0.4.0 answers both names, so a v0.3.x
client against a v0.4.0 peer and a v0.4.0 client against a v0.3.x peer
both still bootstrap; v0.5.0 deletes the old names, after which a
v0.3.x client cannot open a session on a v0.5.0 peer.

## Known gaps (current behaviour)

- User federation tokens have no replay protection within their 24 h
  lifetime (bearer semantics; see *Identity and trust*).
- No protocol version negotiation; compatibility is by release.
- `/federation/report-user` is at-least-once without a relay id: a
  report whose acknowledgement was lost can arrive twice at the home
  instance.
- A key-rotation announcement that cannot be delivered within 24 h is
  dead-lettered; the peer has to be re-paired by hand.
- Presence pushes are best-effort (transient); a peer that is down
  during a status change learns it on the next one.
- Shadow avatars/banners are pulled from the home's `/public/` path on
  first sight and on forced profile sync; there is no push of the file
  bytes.

## Invariants

1. Advertised domain = identity. Never trust the transport host.
2. publicId is the only identity that crosses the wire; shadow users
   (keyed on home instance + publicId) are the only local
   representation of remote users, and only a user's home can vouch for
   them.
3. Peer public keys are pinned at accept time; verification never
   refetches. The only ways a pin moves are a signed `key-rotation`
   confirmed by the peer's `/info`, or a re-`request` confirmed the same
   way — and the previous key verifies for 24 h after either.
4. Instance-level federation config is instance-owner-only.
5. Every relay is queued, at-least-once, and every receiver is
   idempotent; every fire-and-forget relay has a rejection handler.
6. Every peer-supplied value is bounded before it is stored or
   forwarded; every outbound call dials a validated address through
   `federationFetch` with a capped body.
7. Plaintext DM/message content crosses only inside E2EE envelopes when
   the conversation is E2EE — the relay endpoints carry ciphertext
   opaquely (see `e2ee-sender-keys.md`).
