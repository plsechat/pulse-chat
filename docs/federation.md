# Federation — wire protocol and invariants

How two Pulse instances peer, share servers, and relay users, DMs, and
E2EE material. Server code: `apps/server/src/http/federation*.ts`
(inbound endpoints), `apps/server/src/utils/federation*.ts` (keys,
tokens, outbound dispatch), `apps/server/src/routers/federation/`
(operator/user tRPC surface).

## Identity and trust

- **The advertised domain is canonical.** An instance is identified by
  `config.federation.domain` — the value it advertises, not whatever
  host a request happens to arrive on. Peer rows, token issuers, and
  discovery all key on it.
- **One EdDSA (Ed25519) keypair per instance**, generated by the
  instance owner (`federation.generateKeys`), stored in
  `federation_keys`. Public keys are exchanged at peering time and
  pinned in `federation_instances` — later requests are verified
  against the pinned key, not re-fetched.
- **Federation tokens are JWTs** signed with the instance key:
  `iss` = advertised domain, verified against the pinned public key of
  a known, non-blocked peer. Signed payloads use canonicalized JSON
  (sorted keys) so signatures are stable; a JTI replay window
  (~5 min TTL, 10 min retention) rejects replays.
- **publicId is the only cross-instance user identity.** Numeric row
  ids never travel as identity — both sides mint their own serials.
  A remote user materializes locally as a **shadow user** looked up
  (or created) by publicId
  (`findOrCreateShadowUser` / `findOrCreateShadowUserByPublicId`).

## Peering lifecycle

`pending → active` (or `blocked`), direction `outgoing | incoming |
mutual`. All instance-level peering operations (add / accept / block /
remove / list, config, key generation) are gated on
`instanceOwnerProcedure` — the bootstrap-server owner alone, never
per-server permissions.

1. A's owner adds B by domain → `GET /federation/info` (B's identity +
   public key) → `POST /federation/request` (A introduces itself).
2. B's owner accepts → `POST /federation/accept` → both sides hold
   pinned keys, status `active`.

## Endpoint inventory (`apps/server/src/http/index.ts`)

| Group | Endpoints |
| --- | --- |
| Peering | `GET /federation/info`, `POST /federation/request`, `/federation/accept` |
| Discovery | `GET /federation/servers*`, `POST /federation/shares-server` |
| Users | `POST /federation/user-info`, `/federation/user-info-update`, `/federation/report-user` |
| Social | `POST /federation/friend-request`, `/friend-accept`, `/friend-remove` |
| DMs | `POST /federation/dm-relay`, `/dm-group-create`, `/dm-group-add-member`, `/dm-group-remove-member`, `/dm-channel-state-update` |
| E2EE | `POST /federation/get-prekey-bundle`, `/dm-sender-key`, `/channel-sender-key-notify`, `/identity-rotation-broadcast` |
| Moderation | `POST /federation/member-removed` |

Remote users also join servers live over WS: a federated client opens a
WS to the remote instance authenticated by federation token (no
handshake/join), and the remote side resolves it to the shadow user.

## Outbound discipline

- All outbound calls go through `federationFetch`
  (`utils/federation-fetch.ts`): hardened URL validation, per-peer
  token-bucket rate limit, bounded responses.
- Dispatch helpers (`utils/federation-*-dispatch.ts`) fan out to peers.
  Fire-and-forget relays (`void relayFederatedSkdm(...)` etc.) MUST
  carry a `.catch` — an unguarded rejection inside their DB preamble is
  the CONNECTION_ENDED CI-flake family.

## Moderation propagation

Kick/ban of a federated member sends `POST /federation/member-removed`
to the member's home instance, which removes the membership locally and
notifies the user. Bans are recorded on the serving instance; the home
instance is told only about removal.

## Invariants

1. Advertised domain = identity. Never trust the transport host.
2. publicId is the only identity that crosses the wire; shadow users
   are the only local representation of remote users.
3. Peer public keys are pinned at accept time; verification never
   refetches.
4. Instance-level federation config is instance-owner-only.
5. Every fire-and-forget relay has a rejection handler.
6. Plaintext DM/message content crosses only inside E2EE envelopes when
   the conversation is E2EE — the relay endpoints carry ciphertext
   opaquely (see `e2ee-sender-keys.md`).
